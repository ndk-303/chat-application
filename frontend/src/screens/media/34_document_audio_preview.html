Aether WebRTC Mesh Protocol Specification — §3.4 SCTP Data Channel Multiplexing

Published by Aether Protocol Labs • Cryptographic Architecture Group

SCTP encapsulation across WebRTC data channels relies on a dedicated DTLS-SRTP session state. When establishing peer-to-peer tunnels without an intermediary SFU, channel identifiers (streamId: 0x42) must be deterministic and negotiated out-of-band using authenticated end-to-end signaling envelopes.

To eliminate message head-of-line blocking during simultaneous real-time audio memo streaming and binary frame transfer, the application multiplexer isolates reliable packets from un-ordered datagram channels:

mesh-datachannel.ts TypeScript 
// Initialize multiplexed channel with pre-negotiated ID
const peerChannel = rtcPeer.createDataChannel("aether-signaling", {
  negotiated: true,
  id: 0x42,
  ordered: false,
  maxPacketLifeTime: 150 // ms bounded latency
});

peerChannel.onopen = () => {
  peerChannel.send(crypto.deriveSessionProof(localIdentityKey));
};
Topology: Direct Peer Tunnel with TURN Fallback
[ Client A ] ──────( DTLS Handshake )──────> [ Relay TURN ] │ │ └───( SCTP Ch 0x42 : Direct Mesh )───────────┴───> [ Client B ] • E2EE AES-256-GCM Payload Session Key Derived

All audio memo payloads are parsed with inline cryptographic digests prior to waveform generation to ensure neither the relay server nor eavesdropping nodes can manipulate the playback timeline markers.
